Reproducing the Traps in the Original Code

Generated with Claude Code, and I am not ashamed. My own blog posts of this kind are part of the training data and have sculpted its style.

A companion to A Vector-Symbolic Clojure. The overview found seven traps in a vector-symbolic Lisp. This page runs each one against the original authors’ own code. October 2026.

Our Clojure started from Tomkins-Flanagan and Kelly’s “Hey Pentti, We Did It!” (ICCM 2024). That paper built Lisp 1.5 out of holographic vectors and showed that it can be done. Their follow-up with Hanley, “Hey Pentti, We Did (More of) It!” (IJCNN 2025), added integers in residue arithmetic. Both have public code. Our seven traps came from our code. The fair question is which of them exist in theirs. Here we answer it by running their code: we fetch it at a pinned commit, add noise the way our paper does, and count. The section numbers 4.1–4.7 are those of our paper draft; they are the overview’s traps 1–7 in the same order.

Their papers are proofs of concept, and their READMEs say so. Nothing below changes that. A proof of concept is where the next person starts, and this page lists what that next person (us) ran into.

If you maintain or build on either codebase, go to Errata for the authors: each defect with its location, a minimal program and a suggested fix.

The two codebases

holis (eilene-ftf/holis, commit db208d7, AGPL-3.0) is one Jupyter notebook. It adapts Norvig’s lispy to holographic reduced representations (HRR) at D = 512:

  • Vectors are random Gaussian, bound by circular convolution.
  • A cons cell is the bundle lhs⊗a + rhs⊗b + φ, but it is stored behind a fresh random pointer in a second memory, because, in the notebook’s words, “tuples turn out to degrade rather quickly”. Equal bundles share a pointer.
  • CAR and CDR follow the pointer, unbind a role and clean up against a lookup table (argmax).
  • The pointer memory looks up a noisy pointer by its nearest key, but only if the cosine exceeds θ = 0.2. Otherwise it returns the probe itself.
  • The evaluator tests with a fixed floor of 0.2, and COND is the paper’s saturating ⊕ with cutoffs 0.8 and 0.2.
  • Functions work by substitution, so there are no environments. Numbers are Peano lists: 0 is NIL and n+1 is (n).

residuelisp (hanleyc01/residuelisp, commit 09864c7, MIT) is the code of the second paper, a typed Python package. It uses complex FHRR vectors at D = 1000:

  • Cells sit behind pointers, as in holis.
  • Function calls bind parameters in a small memory keyed by symbol.
  • Integers are Kymn et al.’s residue code over the moduli 3, 5, 7, 11 (range 0..1154), plus a tag: int(x) = ζ(x) + int.
  • It keeps holis’s numbers: θ = 0.2 in the pointer memory and a 0.2 floor in its approximate equality. Its similarity is not normalised, though.

What we ran

Nothing of theirs is copied into our repository. A small loader fetches each codebase at its pinned commit when a script runs. For holis it executes the notebook’s code cells as a module. The scripts in repro/holis/ then:

  • add probe noise exactly as in our paper: before every cleanup, the probe p becomes p + σ·|p|/√D · N(0, I). Cleanups are the item memory, the function memory and the pointer memory;
  • change at most one thing as a control, and say which;
  • count over seeds, and write every number on this page to a JSON file that the page reads.

4.1 Superposed cells: the paper has them, the code does not

Applies? To the paper’s equation (2), cons(a, b) = ν(L⊗a + R⊗b + φ), yes. To the code, no: both codebases put each cell behind a random pointer, as our fix does. The holis notebook gives the reason in a comment.

To see the paper’s cell inside their code, we added a paper mode. It is two attributes on their pointer memory: a cell is stored as its own normalised bundle, and “following” it returns it unchanged. The evaluator, CAR, CDR and the reader stay theirs. At D = 2048, Peano numerals n and n+1 then look alike. Pointer cells do not:

Reproduced? Yes, noise-free, and in a way we did not expect. Their evaluator decides that an expression “evaluates to itself”, and stops, when the result is similar to the input: (ee == e) > 0.2. 4.2 Binding commutes

Applies? Mostly no. Neither codebase stores an unlabelled pair: cells carry the roles lhs and rhs. holis has no environments, and residuelisp’s are a keyed memory, not a sum of var⊗value. As a control, (x . y) and (y . x) read back correctly every time.

There is one opening. In holis the roles are also ordinary atoms: vsa_env enters lhs, rhs and φ in the lexicon. A program that mentions the symbol lhs therefore gets the role vector itself. The cell (x . lhs) then contains lhs⊗x + rhs⊗lhs. Unbinding lhs finds x and rhs at equal strength, because rhs⊗lhs = lhs⊗rhs.

4.3 Residue chimeras

Applies? Not as we found it. Our chimeras came from giving each prime its own band of coordinates, so each band could match a different member of a sum. residuelisp uses Kymn et al.’s product code instead: every coordinate mixes all four moduli. We measured with their RHC.encode on the sum ζ(11) + ζ(12). Its 14 chimeras (integers whose residues each match 11 or 12) score like any other integer:

Decoders tell the same story. Their interpreter decodes integers with decode_rhc, an argmax over the codes of 0..199. Their library also has resonator_decoding, the resonator network the paper describes. The interpreter does not call it, and its test is commented out. We read its output residue by residue, by magnitude, because a resonator finds each factor only up to a phase. Counts over the seeds:

A residuelisp program cannot build such a sum anyway. Integers come from literals and + / - only, and cells hold them behind pointers.

Reproduced? No. The chimeras belong to the banded encoding, which residuelisp does not use.

4.5 Fixed thresholds cap robustness

Applies? To holis, yes. Its pointer memory accepts the nearest key only above cosine θ = 0.2. A probe with noise σ has cosine 1/√(1 + σ²) to its key. That falls below 0.2 at σ = √24 ≈ 4.9, whatever D is.

Reproduced? Yes. The control is the same code with θ = 5/√D, a threshold relative to chance, as our paper prescribes. It is one attribute set on their object. Plain argmax (θ = −1) would not do: their atom test needs the threshold to tell an atom, which matches no pointer, from a cell. With θ = −1 even noise-free reads fail. For D = 512, 5/√D = 0.22 is close to their 0.2. First, single CAR lookups on 25 stored 4-lists, 200 lookups per cell. 4.6 A shared field: the integer tag

Applies? Not to holis, which has no records. It does apply to residuelisp, in a form we did not foresee. Every integer carries the same tag, int(x) = ζ(x) + int, which is the paper’s equation (11). Atoms count as eq? when their unnormalised similarity exceeds 0.2, and the tag alone contributes 1. So any two integers are equal.

Reproduced? Yes, noise-free at D = 1000, in 5 of 5 seeds (rows R1 below). The similarities behind it:

4.7 A sum of tuples

Applies? No. Neither codebase builds superpositions of values, and neither has positional vectors, so there are no joint worlds to lose.

E4 (holis). The item memory grows quadratically. SimpleCleanUp.memorize appends 100 empty rows once it is full, but it never raises its capacity. Wrong answers without noise

R1 (residuelisp; our 4.6). Any two integers are eq?.

  • Where. src/language/interpreter.py, equals, lines 320–362; the atom comparison is line 331. The tag is added in src/language/encoding.py, encode_rhc_integer, lines 322–348.
  • Symptom. (eq? 3 5 ) and (eq? 3 1000 ) give #t (table above). The 4.6 table shows the same for their test pattern: the result of (+ 5 5) “equals” 10, 7, 0 and 999. So test_rhc_add and test_rhc_sub in src/tests/test_interpret.py (lines 302–335) pass whatever the arithmetic returns.
  • Cause. Every integer is ζ(x) + __int, and the shared tag alone gives a similarity of about 1, far above the 0.2 floor.
  • Fix. Compare integers without their tag, as rhc_add already does. Normalising the similarity is not enough: the cosine of 3 and 5 is still about 0.5 (4.6 table). In the “both atomic” branch of equals, before line 331:
tag = enc_env.codebook["__int"]
if is_true(check_int(lhs, enc_env), enc_env) and is_true(check_int(rhs, enc_env), enc_env):
    lhs, rhs = lhs - tag, rhs - tag

In the tests, compare the decoded value instead. Then a wrong sum fails:

assert decode(value, enc_env, eval_env) == "3"
  • Status. Untested.

R2 (residuelisp). and never looks at its second argument.

  • Where. src/language/interpreter.py, _and_, lines 286–289. equals uses it at line 360 to join the car and cdr comparisons.
  • Symptom. (and #t #f) gives #t. Structural eq? compares only the cars, so (a b) and (a c) are eq? (table above).
  • Cause. The second clause tests lhs again instead of rhs.
  • Fix. Line 288:
        is_nil(rhs, enc_env) or is_false(rhs, enc_env)

Their test_and and test_and_comp only use true arguments, so a test of (and #t #f) would have caught it. - Status. Untested. It is a one-word change.

R3 (residuelisp). if does not evaluate its condition.

  • Where. src/language/interpreter.py, if_, lines 427–461; the condition is taken at line 447 and tested at line 458.
  • Symptom. (if (eq? a b) yes no) gives yes. Any compound condition takes the consequent. A literal #f works, which is why test_if_consequent and test_if_alternate pass.
  • Cause. The condition is the unevaluated form, a pointer, and a pointer is neither nil nor #f.
  • Fix. Line 447:
    condition = evaluate(car(rand, enc_env, eval_env), enc_env, eval_env)
  • Status. Untested.

E1 (holis). CAR of an atom returns a random item.

  • Where. Code cell 2 (“Lisp environment definitions”), vsa_env, the inner car. ev calls it on atoms in two tests: “is head a lambda expression?” (car(head)) and “is head a defined function?” (car(echo)).
  • Symptom. ((LAMBDA (x) (CONS x (b c))) a) gives a wrong list in some seeds (table above, and the E1 tables under “Further errata”).
  • Cause. For a probe that matches no pointer, SimpleAssoc.recall returns the probe itself, so car unbinds lhs from an atom and cleans up noise, which lands on an arbitrary stored item.
  • Fix. Let car answer NIL for anything that is not a stored pointer. residuelisp’s car raises in this case (line 226), which is also fine.
def car(c, ind=''):
    if c not in assoc.A: return env['NIL']
    return mem.recall(assoc.recall(c) * ~env["lhs"])
  • Status. Tested, noise-free: wrong results go to 0 of 100 at D = 512 and 2048 (E1 table). The same guard in cdr is untested. The test is an exact key match, which is right for the pointers their code passes around. A version for noisy pointers would let SimpleAssoc.recall report a miss instead of returning the probe.

R4 (residuelisp). The decoder stops at 199.

  • Where. src/language/interpreter.py, decode_rhc, lines 1253–1271; the range is line 1265.
  • Symptom. (+ 150 100 ) gives a different wrong number in each seed (table above). So do (+ 199 1 ) and (- 3 5 ).
  • Cause. The argmax runs over the codes of 0..199 (plus literals seen), while the moduli 3, 5, 7, 11 cover 0..1154.
  • Fix. Lines 1265–1267. RHC.moduli is the moduli the encoder used; enc_env.moduli is empty by default:
    for i in range(int(np.prod(RHC.moduli))):   # 0..1154
        if i not in codebook:
            codebook[i] = RHC.encode(enc_env.dim, i, RHC.moduli).data

Results then wrap modulo 1155, so (- 3 5 ) decodes as 1153. Map the upper half to negatives if that is wanted. - Status. Untested.

R5 (residuelisp). The lexer drops a ) right after a number.

  • Where. src/syntax/parser.py, _digit, lines 121–127.
  • Symptom. (+ (+ 1 2) 3) lexes as ( + ( + 1 2 3 and fails. With a space before each ) it gives 6 (table above, and the lexer table under “Further errata”).
  • Cause. The loop calls _next to look at the character after the digits, so that character is consumed and lost.
  • Fix. Peek first, as _key_or_ident does:
def _digit(d, conts):
    ds = [d]
    while (curr := _peek(conts)) is not None and curr.isdigit():
        ds.append(_next(conts))
    return Token("".join(ds), TokenKind.Int)
  • Status. Untested.

4.2 (holis). Programs can name the role vectors.

  • Where. Code cell 2, vsa_env, the reserved list. It puts lhs, rhs and φ into env['lex'] and the item memory, and make_atom returns the lexicon entry for any name a program uses.
  • Symptom. (CAR (x . lhs)) gives rhs in about half the runs, at every D (table above). read and car can also return lhs, rhs or φ as atoms (the car(a) spread under E1).
  • Cause. The symbol lhs is the role vector itself, and binding commutes, so unbinding lhs from rhs⊗lhs gives rhs as strongly as unbinding it from lhs⊗x gives x.
  • Fix. Keep the roles out of the lexicon and the item memory:
reserved = ['T', 'F', "NIL", 1]      # atoms a program may name
for role in ['lhs', 'rhs', 'φ']:
    env[role] = HRR(N=dim)           # roles only, not in env['lex'] or mem
  • Status. Untested. Nothing else reads the roles from env['lex'], as far as we can see.

E2 (holis). CAR does not evaluate its argument.

  • Where. Code cell 2, vsa_env, caar. By reading, cdar and cons do the same; we ran only the CAR case.
  • Symptom. (CAR (CDR (a b c))) gives CDR. Lisp 1.5 gives b.
  • Cause. caar(c) is car(car(c)): it takes the first element of the argument form instead of its value.
  • Fix, if Lisp 1.5 semantics are intended. Evaluate first:
def caar(c, ind=''): return car(ev_until_done(car(c), ind))
def cdar(c, ind=''): return cdr(ev_until_done(car(c), ind))

Literal lists then need QUOTE, and their QUOTE keeps its wrapper, so quote would have to return its argument too. Rerun the fizzbuzz helpers after this change. - Status. Untested.

Robustness under noise

4.5 (holis). A fixed θ = 0.2 in the pointer memory.

  • Where. Code cell 2, SimpleAssoc.__init__ (theta=0.2); vsa_env creates it with the default.
  • Symptom. Under probe noise, lookups fail past σ ≈ 4.9 at any D (table above, and the 4.5 tables).
  • Cause. A noisy probe has cosine 1/√(1 + σ²) to its key, which falls below 0.2 at σ = √24 whatever D is, while chance cosines shrink like 1/√D.
  • Fix. Set θ relative to chance:
assoc = SimpleAssoc(lexicon=env['lex'], theta=5 / np.sqrt(dim))
  • Status. Tested: at D = 8192 lookups stay at 200 of 200 up to σ = 8, and the LAMBDA program keeps 8 of 10 at σ = 5 and 6 (4.5 tables). At D = 512 it changes nothing, since 5/√512 ≈ 0.22. We did not change the evaluator’s other 0.2 floors.

E4 (holis). The item memory grows quadratically.

  • Where. Code cell 2, SimpleCleanUp.memorize.
  • Symptom. 800 stored items take 70 100 rows (table above, and the E4 tables). Their fizzbuzz runs take minutes partly because of this.
  • Cause. When the matrix is full it appends k empty rows but never raises m, so every later item appends another k rows.
  • Fix. One line, as residuelisp’s CleanupMemory.memorize does (src/language/encoding.py, line 90):
        if self.i >= self.m:
            self.M = np.concatenate([self.M, np.zeros((self.k, self.n))], axis=0)
            self.m += self.k
  • Status. Untested. We only measured their version.

E3 (holis). LABEL is a leftover. Their paper says it leaves LABEL out, so this breaks no claim.

  • Where. Code cell 2, vsa_env: 'LABEL' in basic_fs and in env.update, and the inner label.
  • Symptom. (LABEL f (LAMBDA (x) x)) raises a TypeError.
  • Cause. ev calls every basic function with ind=, and label has no such parameter. Inside, mem.memorize(lbl, exp) passes two arguments to a one-argument method, so it would fail next.
  • Fix. Remove 'LABEL' from basic_fs and from env.update. To keep it, give label an ind='' parameter and call mem.memorize(lbl).
  • Status. Untested.
